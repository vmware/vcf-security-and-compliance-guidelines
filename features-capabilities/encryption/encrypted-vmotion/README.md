# Encrypted vMotion

VMware vSphere Encrypted vMotion protects VMs as they live-migrate between ESX hosts using vMotion.

## How to Get Started

Each virtual machine has a vMotion encryption setting. The default, 'Opportunistic', encrypts the migration traffic when the CPUs on both hosts support AES-NI, which all currently supported x64 CPUs do. 'Required' makes the vMotion fail rather than proceed unencrypted. 'Disabled' turns encryption off.

You can also configure vMotion encryption settings in bulk using PowerCLI:

```powershell
foreach ($VM in Get-VM) {
    $VMview = Get-View -VIObject $VM
    $ConfigSpec = New-Object VMware.Vim.VirtualMachineConfigSpec
    $ConfigSpec.MigrateEncryption = "required"
    $VMview.ReconfigVM_Task($ConfigSpec)
}
```

## Questions & Answers

### Do I need a KMS for Encrypted vMotion?

No. Encrypted vMotion does not use a KMS, as the encryption keys used are ephemeral and not stored anywhere except temporarily in memory of vCenter and the two ESX hosts involved.

### How does this impact VM performance?

There is [a paper from the VMware Performance team](https://www.vmware.com/content/dam/digitalmarketing/vmware/en/pdf/techpaper/performance/encrypted-vmotion-vsphere65-perf.pdf) on the effects of Encrypted vMotion on system performance. It was written for vSphere 6.5 but the findings still hold today, and newer CPUs help mitigate the effect even more. In short, there is CPU overhead, but it’s only while the vMotion is occurring, and it is minimal.

### What additional components do I need to enable Encrypted vMotion?

Nothing. Encrypted vMotion is a native part of Cloud Foundation and vSphere and can be enabled directly on VMs.

### If I use encrypted vMotion, do I still need to have an isolated vMotion network?

There are several reasons why having a separate network segment for vMotion can be a good idea:

1. It can help prevent vMotion traffic from being routed through the management network, where the traffic would be exposed to a wider set of systems and users. In fact, you can make the VLAN you use a "non-routable" VLAN, which keeps that traffic from being routed in or out of the segment. This may have implications for cross-vCenter vMotion, though.
2. It can help administrators manage the vMotion traffic, which might aid in troubleshooting network performance issues. However, Network I/O Control can also be used to apply QoS policies to vMotion traffic.
3. A separate network segment could have DHCP enabled, which would allow the vMotion interfaces to automatically obtain IP addresses and reduce some system administration overhead.

Because a VM's vMotion encryption can be set to Disabled, we still recommend isolating vMotion traffic.

### Does Encrypted vMotion work with Storage vMotion?

Yes. Storage vMotion continues to work in the same way.

### Does an encrypted VM use Encrypted vMotion?

Yes. A VM that is protected with VM Encryption will require encrypted vMotion.

### If encrypted vMotion is left at the default "Opportunistic" setting, is my migration actually encrypted?

Yes, in virtually all cases. Opportunistic means vMotion is encrypted whenever the CPUs on both the source and destination hosts support AES-NI, and every currently supported x64 processor does. In practice, that means Opportunistic vMotions are encrypted. The only time Opportunistic falls back to unencrypted is on hardware without AES-NI. If you want the migration to fail rather than proceed unencrypted, set the per-VM mode to "Required."

### Can I require Encrypted vMotion for all vMotions in my cluster?

Encrypted vMotion is a setting on each VM, but not at the cluster level. You can use PowerCLI to set it on all your VMs, such as the example cited above in "How to Get Started."

### How do I use vSAN Encryption with Encrypted vMotion?

In exactly the same way as you would with normal vMotion. The two features operate independently of each other.

### Does Encrypted vMotion cause a VM to be slower?

Encrypted vMotion only happens when a VM is being migrated between hosts and does not affect VM performance at other times.

### Does Encrypted vMotion cause a VM to migrate more slowly?

Any use of encryption costs some performance. However, vMotion is a background process, and CPU cycles are usually the most fungible resource in a cluster, so the overhead is not significant, even for large environments, workloads, and hosts. This is especially true for vSphere 7 and later, which improved vMotion performance.

### Where are the encryption keys stored?

Encrypted vMotion uses a temporary, one-time 256-bit cryptographic key generated by vCenter and shared with the source and destination ESX hosts for use by that single vMotion operation. After the vMotion is complete the key is discarded and never reused, and it is never stored anywhere but memory.

### How can I make sure that the encryption keys are purged from memory?

Given the reality of hardware vulnerabilities and other factors in computer hardware design that may cause data in memory to be retained even when the memory is freed by ESX or vCenter, and possibly even through a reboot of the host, the only reliable way to clear memory is to power cycle the hardware.

### How do I allow the encrypted vMotion traffic to be inspected by a network security tool?

This is not supported nor recommended. Allowing a network security tool to inspect vMotion traffic means workload secrets, such as authentication tokens, private keys, and more, will be copied and stored on that system as well, which is a net decrease in security and conflicts with regulatory requirements and security best practices for secret handling. vMotion traffic is also quite bursty and can easily overwhelm a security tool's ability to analyze it.

### How can I get the keys used by encrypted vMotion to allow decryption of the vMotion traffic?

There is no mechanism to retrieve the keys used by encrypted vMotion.

### Does Encrypted vMotion use TLS?

No. For performance & workload isolation reasons the transfer between ESX hosts does not use TLS. Instead, it uses 256-bit AES-GCM algorithms which are FIPS-validated. If a vMotion is between hosts managed by different vCenters in Enhanced Linked Mode the vCenters will protect their communications using TLS. The key distribution communications between vCenter and the ESX hosts is done over a connection protected by TLS.

### Is vMotion supported between two hosts where one has a physical TPM and the other does not?

Yes. The presence or lack of a physical TPM does not impact vMotion.

### Can encrypted vMotion offload its encryption work to hardware?

Yes. Starting in VCF 9.1, encrypted vMotion can offload its AES-GCM encryption to Intel QuickAssist Technology (QAT) hardware instead of performing it on the host CPU. Because encrypting live-migration traffic is normally a per-migration CPU cost, moving that work to a QAT accelerator frees host CPU cycles during migrations. The benefit is greatest on busy hosts and during large evacuations, when many VMs migrate at once.

### What do I need in order to use vMotion encryption offload?

The host must have Intel QuickAssist Technology (QAT) hardware, and SR-IOV must be enabled on the host, because the offload reaches the accelerator through QAT SR-IOV virtual functions. The capability is available in VCF 9.1 and newer. With those in place, turn it on with the `Migrate.VMotionEncryptionOffload` advanced setting. Hosts without QAT, or with SR-IOV disabled, simply use the host CPU's software AES-GCM encryption instead.

### How do I enable or disable vMotion encryption offload?

The offload is controlled by the ESX advanced setting `Migrate.VMotionEncryptionOffload`: set it to `1` to enable and `0` to disable. The Security Configuration Guide covers this as the `esx-9.vmotion-encryption-offload` control, with audit and remediation examples.

### What happens if QAT hardware isn't present or is busy?

Offload is designed to fall back gracefully. If a host has no QAT accelerator, or the accelerator is contended (for example, a VM using QAT or DVX passthrough powers on and needs the resource), encrypted vMotion releases the accelerator and continues using the host CPU's software AES-GCM encryption, and the migration completes normally. Migrations also work between mismatched hosts, for instance where the source has QAT and the destination does not. (One 9.1 caveat: this graceful fallback applies to resource contention and absence. If the QAT device itself returns an error, the vMotion fails rather than falling back to CPU encryption.)

### Does offload change which encryption modes I can use?

No. Offload is independent of the vMotion encryption mode. It works whether the per-VM mode is Required, Opportunistic, or Disabled, and offload can be on or off in each case.

### We have a FIPS requirement. Does the QAT offload affect FIPS compliance?

It can. When encryption runs on the host CPU it uses ESX's FIPS-validated software cryptography. When it is offloaded, the cryptography runs in the QAT accelerator's firmware, which is supplied by your hardware vendor rather than Broadcom. If you are obligated to meet FIPS 140-3, confirm that the server's QAT firmware is FIPS 140-3 validated. If it is not, disable the offload (`Migrate.VMotionEncryptionOffload = 0`) so vMotion encryption stays on ESX's validated software cryptography.
